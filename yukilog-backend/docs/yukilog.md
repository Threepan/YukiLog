## 细腰模型

所谓 **细腰模型**，指的是一种非常自然、也几乎不可避免的软件结构形态：

> **两头规模巨大，中间高度收敛**

* **上端**：用户世界
页面、交互、审美、习惯、情绪、设备……复杂而不可控

* **下端**：底层基础设施
数据库、文件系统、网络、硬件、操作系统……复杂且冷酷

* **中间**：程序员精心雕刻出来的“腰部”
用抽象、接口和约定，把混沌压缩成秩序

不管是后端常说的 **面向对象 / 接口 / 分层**

还是前端熟悉的 **组件 / 路由 / 状态管理**

它们本质上都在做同一件事：

> **通过抽象与封装，把复杂世界压缩成可组合的简单接口**

用户的一句

> 「我要看这个页面」

在系统内部, 会被层层翻译为:

> 请求数据 → 处理业务 → 组织结果 → 渲染界面

**细腰模型不是设计出来的，而是复杂系统在长期演化中“长出来的形态”**

#### 细腰模型在 YukiLog 中的体现 🐾

```text
┌──────────────────────────────┐
│   现实世界 / 用户行为 / 输入     
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│        前端（UI / 状态）       
│    页面、交互、路由、组件树     
└──────────────┬───────────────┘
               │  JSON / HTTP
               ▼
┌──────────────────────────────┐
│     Handler 层（接口边界）        
│     · 参数校验                    
│     · 鉴权 / 鉴权失败即返回        
│     · Rust 类型 ⇄ JSON      
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│    Service 层（✨细腰核心✨）     
│    · 业务规则                    
│    · 用例编排                    
│    · “我要做什么”                
│    · 与 HTTP / DB 完全无关        
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│    Repo 层（领域数据访问）       
│    · 强类型 Domain Model         
│    · 封装 CRUD 原子操作          
│    · 隔离数据库实现细节           
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│    ORM 层（数据翻译）             
│    · SQL ⇄ Rust 类型             
│    · 行 → 结构体                 
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│    PostgreSQL                    
│    · 将复杂无序的数据             
│    · 整理为结构化、有约束的存储   
└──────────────────────────────┘

```

#### (1) **`view_count` 要防刷吗**

这个字段是用来记录浏览量的, 主题, 标签, 文章都有他的身影

###### Q: 要是文章每次被访问都会增加浏览量好不好?

当然好! 我希望自己的文章浏览量超级超级多!

但是 ... 不可以!!! 必须要做防刷

不然坏人直接写一个 `curl` 脚本多挂几个进程, 不就直接数值溢出把我打爆了吗?
