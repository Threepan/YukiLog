## 细腰模型

所谓 **细腰模型**，指的是一种非常自然、也几乎不可避免的软件结构形态：

> **两头规模巨大，中间高度收敛**

* **上端**：用户世界
页面、交互、审美、习惯、情绪、设备……复杂而不可控

* **下端**：底层基础设施
数据库、文件系统、网络、硬件、操作系统……复杂且冷酷

* **中间**：程序员精心雕刻出来的“腰部”
用抽象、接口和约定，把混沌压缩成秩序

不管是后端常说的 **面向对象 / 接口 / 分层**

还是前端熟悉的 **组件 / 路由 / 状态管理**

它们本质上都在做同一件事：

> **通过抽象与封装，把复杂世界压缩成可组合的简单接口**

用户的一句

> **「我要看这个页面」**

在系统内部, 会被层层翻译为:

> **请求数据 → 处理业务 → 组织结果 → 渲染界面**

**细腰模型不是设计出来的，而是复杂系统在长期演化中“长出来的形态”**

## 软删除

软删除的意思是, 不直接删除数据, 而是将数据标记为 "delete", 以后想要恢复数据, 只需要取消这个标记

> **Q: 为什么不做? 他会带来什么问题?**

因为这个业务说起来简单, 但复杂度其实非常高!

软删除的概念虽然是对删除的优化, 但底层实现其实是 **对删除的否定**

> **问题是："将 `status` = `deleted`" 这句话只在 数据库层 成立。**

一旦进入 **领域模型 / 服务层 / 查询层**，麻烦就开始指数级增长。

#### 简单列举几个麻烦

> **(1) 软删除在数据库的表现**

软删除的记录其实仍然存在于数据库中, 并且如果你的数据库写了 **UNIQUE** 约束, 就必须让数据库兼容软链接的处理 ...

于是你就会开始添加规则, 企图让数据库在检索时忽略那些 **delete**

* `UNIQUE (slug, status)`
* `WHERE status != 'deleted'`

> **结果会导致 `INDEX` `SELECT` `ORM` 复杂度直线上升, 全系统被迫要去维护一个幽灵条件**

> **(2) 无视架构越权操作**

> 软删除与状态流转操作，本质上是在做 创建 / 删除 一条记录
> 
>但它的逻辑又不是新建记录，只是修改一个列

一般操作一条记录, 一定会走完 `handler` -> `service` -> `repo` -> `orm` -> `db` 整个生命周期

但软删除的逻辑只是 `status` = `active`, 他完整的绕过了所有 `级联逻辑` `领域事件`

> **如果要为他单独写一套验证逻辑, 为什么不直接重新创建呢 ?**
